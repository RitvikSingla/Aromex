## Summary

Adds a new gateway endpoint, `POST /firestore-token`, that hands the Desktop app a short-lived Google OAuth access token scoped to Firestore only. Desktop (JVM Compose-Desktop) has no Firebase client SDK, so it must reach Firestore via `google-cloud-firestore`, which requires Google credentials — the gateway holds each company's service-account key already and now brokers a narrow token minted from it. The auth block (bearer → `unsafeDecodeProjectId` → `findCompanyByProjectId` → `verifyIdToken` → `isUserActive`) is copied character-for-character from `/hl-token`, so 401/403 shapes and the "trust boundary" are identical. The mint side uses `google-auth-library`'s `JWT` with `scopes: ['https://www.googleapis.com/auth/datastore']` — deliberately never `cloud-platform` — and caches the token per company with a 60 s refresh margin, matching `hlClient`'s pattern. All nine new vitest cases pass (401 missing / 401 invalid / 401 verify-fail / 403 inactive / 200 happy path / cache reuse / cache invalidation / 502 upstream throw / 502 empty-token). Full suite: 26/26 green. No live smoke test in this ticket — that happens at deploy time (recipe in "How to test" below).

## Files changed

**Server — new service** (`aromex-gateway`)
- `src/services/firestoreTokenService.ts` (+130) — `mintFirestoreToken(company)` reads the SA key the same way `firebaseVerifier.ts` does (`readFileSync(company.serviceAccountKeyPath)`), builds a `google-auth-library` `JWT` with `scopes: ['https://www.googleapis.com/auth/datastore']`, calls `getAccessToken()`, reads `jwt.credentials.expiry_date` (millis) for the TTL, and caches both the `JWT` instance (in `jwtCache`) and the minted token (in `tokenCache`) per company. Refresh margin `REFRESH_BEFORE_EXPIRY_MS = 60 * 1000` mirrors `hlClient.ts`. Return shape: `{ firestoreToken, projectId, expiresIn }`. Exports `_resetFirestoreTokenCache()` for tests (parallel to `hlClient._resetTokenCache()`) and a `FirestoreTokenError` class (parallel to `HlUpstreamError`) for upstream failures. The SA key JSON is parsed defensively — missing `client_email` or `private_key` → throw. Comments call out the Approach A security decision (`bypasses rules`, `datastore only, never cloud-platform`, `short-lived and company-scoped`).

**Server — new route** (`aromex-gateway`)

## Deviations / decisions

- **Auth block copied verbatim, not extracted into a shared helper.** The ticket said "Copy the auth block from `hlToken.ts`," and I did — lines 1–52 of `firestoreToken.ts` are the same as lines 1–34 of `hlToken.ts`. Extracting into a shared `requireVerifiedFirebaseUser(app, request, reply)` helper is tempting but was out of scope (would have touched `hlToken.ts`, which the ticket forbids). Worth doing later once a third caller appears.
- **Scope pinned to `datastore` only, never `cloud-platform`.** Enforced by the constant `DATASTORE_SCOPE` at the top of the service. The scope is *not* configurable — hard-coding it was a deliberate call so a future edit can't accidentally widen the blast radius.
- **`FirestoreTokenError` is a new class, not `HlUpstreamError`.** Same shape (extends `Error`), same purpose (upstream-boundary marker). Kept them separate because they signal different upstreams and should be able to diverge without one dragging the other along (e.g. if we later add a status code to `HlUpstreamError`, it shouldn't ripple into Firestore's error surface).
- **`jwt.credentials.expiry_date` used for TTL** rather than parsing the token or hard-coding a value. `google-auth-library` populates that field on the JWT client after `getAccessToken()` returns; falls back to `now + 60 min` if the field is unset (defensive; hasn't happened in tests). Preferred over a hard-coded TTL because Google's actual expiry can vary.
- **`node:fs` mocked with `importActual` fallback.** `readFileSync` is stubbed only for paths ending in `-sa.json`; everything else falls through to the real fs. This keeps Prisma / dotenv / vitest's own file reads working while letting the SA-key stub be per-test.
- **Direct dep pin at `^10.0.0`, not `^9.15.0`.** The plan said `^9.15.0` in error — that's the earlier major. `firebase-admin@13` transitively resolves `google-auth-library@10.7.0`; pinning at `^10.0.0` matches what npm already installed and avoids a duplicate copy in `node_modules`. Verified `10.7.0` still exports `{ JWT }` from the top level (`node_modules/google-auth-library` was already there before this change).
- **Live smoke test deferred to reviewer / deploy step.** The ticket calls for a real `google-cloud-firestore` read to succeed with the returned token. That needs the aromex-test SA + web API key locally (or SSH to the droplet) and both were not in this session's scope. The exact reproducer is Option B in "How to test" and the two crucial checks (Firestore read succeeds; Cloud Resource Manager rejects same token) are called out explicitly.

## Open questions / follow-ups

- **Live Firestore verification.** Option B in "How to test" needs to be exercised before this ships to Desktop. The important assertion isn't just "200 back from the gateway" — it's that the returned token (a) works against `https://firestore.googleapis.com/v1/projects/.../databases/(default)/documents/...` and (b) gets rejected by `https://cloudresourcemanager.googleapis.com/...`. If the second call succeeds, the scope config is wrong and needs investigation.
- **Extract the copied auth block into a shared helper.** Not now (out of scope), but the second occurrence is enough justification. A tiny `src/services/requireFirebaseUser.ts` that returns `{ company, decoded }` or a `FastifyReply` would let both routes shed ~20 lines.
- **`_resetFirestoreTokenCache` is exported for tests.** Matches `_resetTokenCache` in `hlClient.ts`. If we ever wire an admin endpoint to force a re-mint (e.g. after rotating an SA key), it could hang off this — for now it's test-only.
- **SA-key rotation runbook.** Not new to this ticket, but worth noting: rotating a company's SA key requires the same `pm2 restart aromex-gateway` step already documented in `docs/DEPLOY.md § Rotating secrets` (to bust `firebaseVerifier`'s app cache). The Firestore-token JWT cache is now in the same bucket — the restart clears both.
- **No rate limit.** `/firestore-token` sits alongside `/hl-token` under the unrestricted registration. If Desktop misbehaves (e.g. thrashes the endpoint on every user action), we can add a per-user rate limit later; the current cache + expiry give enough headroom to defer.
- **No JVM-side changes yet.** The Desktop app that consumes this endpoint is out of scope per the ticket. When it ships, it will use `FixedCredentialsProvider` + `GoogleCredentials.create(new AccessToken(firestoreToken, expiresAt))` (documented in the API section) to construct its `google-cloud-firestore` client, and re-mint via `/firestore-token` before the token expires.
- **Approach B (proxy) is still deferred.** If future compliance requires per-user rules enforcement on Desktop, Approach B (gateway acts as Firestore proxy, applies rules on the way through) is the fallback. Out of scope now per the ticket's explicit decision.
